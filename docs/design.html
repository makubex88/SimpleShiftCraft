SimpleShiftCraft

A small restaurant shift scheduler. It helps a manager build a weekly labor plan that balances profitability, staff predictability and guest coverage, and it explains every problem in plain English.

💰 Profitability

Weekly labor cost is tracked live against a budget the manager sets.

📅 Predictability

Respects availability and max hours, and blocks "clopening" (closing late, then opening early).

🍽️ Coverage

Every service window shows the staff it needs, so gaps are obvious before publishing.

Scope

In scope (v0.1)

  • Staff, availability, weekly schedule
  • Auto-fill draft schedule
  • Conflict detection (5 rules)
  • REST + GraphQL API, Postgres
  • One-page React week grid

Out of scope (on purpose)

  • Auth / multi-tenant permissions
  • Payroll, time clock, shift swaps
  • Sales forecasting (budget is entered by hand)
  • Mobile app

Why both REST and GraphQL?

GraphQL for reads

The week view needs staff, availability, shifts and issues in one round trip. One query replaces four REST calls, and the client asks only for the fields it shows.

REST for writes

Commands like POST /schedules/:id/publish are simple, cacheable at the edge, idempotent where it matters, and easy for third-party integrations.

Both layers call the same service functions, so business rules live in exactly one place. Recorded in docs/adr/001-rest-and-graphql.md. Writes use one idempotent PUT per grid cell, so a retried request can't double-book anyone.

03Data management

PostgreSQL is the system of record. Access goes through one interface, so the storage engine can be swapped.

Principles

DecisionWhy
Money stored as integer centsNo floating-point rounding errors in labor cost
Times stored as timestamptz (UTC) + restaurant timezoneDaylight-saving changes don't break the 10-hour rest rule
Plain SQL migrations (migrations/001_init.sql)Readable and reviewable, no ORM magic
DB constraints back up domain rulesUNIQUE(employee_id, starts_at) stops double-booking even if the API has a bug
Issues are computed, not storedThey're always fresh and there's no sync bug. They're cheap to compute (≈ 50 staff × 14 shifts)
Published schedules are immutableEdits create a new version, so staff can trust what they saw

Repository interface

export interface ShiftRepository {
  getWeek(scheduleId: string): Promise<Week | null>;
  setShift(scheduleId: string, a: { employeeId, day, slot | null }): Promise<void>; // idempotent
  replaceShifts(scheduleId: string, shifts: Assignment[]): Promise<void>;  // one transaction
  publish(scheduleId: string): Promise<void>;
}

05UI / UX

Designed for a busy manager doing the schedule on a Sunday night between services.

Personas

👩‍🍳 Dana, general manager

Goal: publish next week's schedule in under 10 minutes without going over budget.
Pain: spreadsheets don't warn her when someone is double-booked or will hit overtime.

🧑‍🍳 Maria, server

Goal: know her shifts early and never get a "close then open".
Pain: last-minute changes and schedules that ignore her days off.

Design principles

PrincipleHow it shows up
One screen, one jobThe whole week is visible at once, with staff in rows and days in columns. No modals for normal edits
Fast by defaultClick a cell to cycle Off → AM → PM. "Auto-fill" builds a draft in one click
Explain, don't just blockEvery issue is a human sentence with names and times, not an error code
Errors vs warningserror blocks publishing (staff are harmed). warning lets the manager decide (going over budget can be a fair business call)
AccessibleAM and PM differ by label, not just colour. Cells are real <button>s, so they work with a keyboard. Contrast is WCAG AA

Issue copy (examples)

RuleSeverityMessage shown
Availabilityerror"Aoife isn't available on Mon."
Clopeningerror"Liam closes Tue 23:00 and opens Wed 07:00, which is only 8h rest (min 10h)."
Max hourserror"Maria is at 40h this week (max 32h)."
Coveragewarning"Fri PM needs 2 people, has 1."
Budgetwarning"Labor is €2,240, which is €90 over budget."

    07Flowcharts

    Auto-fill algorithm (greedy, explainable)

    This is a deliberately simple greedy pass. It's predictable and easy to explain to a manager, and it runs in O(slots × staff). A constraint solver can replace it later behind the same function signature.

    flowchart TD
  A(["Manager clicks Auto-fill"]) --> B["Load staff, availability, coverage rules"]
  B --> C{"Next open slot? (Mon to Sun, AM then PM)"}
  C -- no --> Z["Run conflict check"] --> Z2(["Return draft + issues"])
  C -- yes --> D["Candidates = all active staff"]
  D --> E["Remove: unavailable that day"]
  E --> F["Remove: already working that day"]
  F --> G["Remove: would exceed max hours"]
  G --> H["Remove: less than 10h rest (clopening)"]
  H --> I{"Anyone left?"}
  I -- no --> J["Leave slot open (coverage warning)"] --> C
  I -- yes --> K["Pick fewest hours so far (tie: lowest rate)"]
  K --> L["Assign shift"] --> C

    08Testing

    What a test looks like

    import { describe, it, expect } from 'vitest';
import { findIssues, autoFill } from './scheduler';
import { seedWeek } from './fixtures';

describe('findIssues', () => {
  it('flags a clopening shift', () => {
    const week = seedWeek({ shifts: [
      { emp: 'liam', day: 'Tue', slot: 'PM' },
      { emp: 'liam', day: 'Wed', slot: 'AM' },
    ]});
    expect(findIssues(week)).toContainEqual(
      expect.objectContaining({ rule: 'clopen', severity: 'error' })
    );
  });
});

describe('autoFill', () => {
  it('produces a week with no errors', () => {
    const result = autoFill(seedWeek());
    expect(result.issues.filter(i => i.severity === 'error')).toEqual([]);
  });
});
